# Seeded spec outfits default to their specialization's icon; all other outfits default to fileID 132724

## Summary
Most of this already works. seedSpecs stores the spec's fileID on rec.icon at seed time, and has done since P4.6 (commit 21c09d9). Separately, NS.OutfitIcon's chosenIcon rung falls back to the SPEC_n trigger descriptor's icon, which is the same spec icon. So a seeded spec outfit should already draw its spec icon, both when it has the stored icon and when the icon was cleared to "Outfitter chooses", as long as its trigger is still SPEC_n. What is missing: (1) a rung keyed on rec.builtin = "SPEC_n", so the icon no longer depends on the trigger staying in place; (2) changing the last rung from the coat-hanger glyph to fileID 132724; (3) keeping the sheet button and broker on the hanger, which they will not be, because they share NS.Constants.DEFAULT_OUTFIT_ICON. Recommend resolving the spec icon at draw time from the cached SPEC_n trigger descriptor (NS.Triggers.Get(rec.builtin).icon). That needs no migration and no new API, and Equipment Manager (EM) icons are never written. Also guard seedOne so it does not write rec.icon on an EM mirror it adopts by name.

## Approach
1) Add a spec rung, resolved at draw time and keyed on the seed key rather than the trigger. In modules/Outfits.lua chosenIcon (:678), before the trigger rung, add:
   `local b = rec.builtin; if type(b) == "string" and b:find("^SPEC_%d+$") then local d = NS.Triggers.Get(b); local s = d and plainIcon(d.icon); if s then return s end end`
   The builtin key is the same string as the SPEC_n descriptor id, so this reuses the cached, PlainNumber-sanitized icon (modules/Triggers.lua:165). It adds no Compat call per row draw and needs no new API. Alternative: Compat.GetSpecializationInfo(tonumber(n)) and its 4th return through Secrets.PlainNumber, but the descriptor is cheaper and already handles the "spec data not ready" retry. The rung sits under ownIcon, so the player's pick still wins: that is "until the player picks another icon". Characters seeded with icon nil, and spec outfits whose trigger was later changed, pick up the spec icon with no migration. Do NOT put it in ownIcon: an EM mirror never carries builtin (EquipmentManager.lua:46 COPY), and its set icon must keep precedence.
2) Keep the seed-time store at Outfits_Seed.lua:166. Removing it would make "Store on server" create the set on 134400, a question mark in Blizzard's EM UI, instead of the spec icon (EquipmentManager.lua:439). Keeping it also leaves the existing test_outfits:282 parity intact. With rung (1) the stored value is redundant for display but harmless.
3) Guard the EM case in seedOne (Outfits_Seed.lua:135-139): when the adopted record has kind == "em", skip `rec.icon = opts.icon`. Optionally skip the builtin/trigger writes too; ask the owner. This means an EM set the player already named "<Class>: <Spec>" keeps its own icon and the mirror never holds a stale rec.icon. Add a red-under test: EM set named "Rogue: Assassination" plus LoadPass leaves rec.icon nil and EM.Icon unchanged.
4) Make 132724 the last rung for outfits only. Add a new constant, for example C.OUTFIT_FALLBACK_ICON = 132724, in core/Constants.lua beside DEFAULT_OUTFIT_ICON. Make NS.OutfitIcon (:700) return `NS.Constants.OUTFIT_FALLBACK_ICON, 1, 1, 1`. PLAIN_ICON stops being needed as a fallback, because a fileID does not depend on the library being present. Leave C.DEFAULT_OUTFIT_ICON, or rename it to something like C.BRAND_ICON / SHEET_BUTTON_ICON, as the coat hanger for Dock.lua:309 and Broker.lua:54 idleIcon. Otherwise the gold sheet button and the broker idle icon become a tinted chest piece. Also check the other recon areas (images 3/4: the yellow hanger button) so the button keeps the hanger.
5) Tests (red under each): test_outfit_icons "a seeded spec outfit draws its spec icon with no stored icon and no trigger" uses scene{class="ROGUE"} and O.Create(..., {builtin="SPEC_2"}); expect 1002, then SetIcon(id, 135349) wins, then SetIcon(id, 134400) brings back 1002. Re-pin test_outfit_icons.lua:75-90 and test_bar.lua:290-315 from HANGER to 132724 on the outfit ladder. Keep test_dock.lua:472 and test_broker.lua:86 on the hanger. Add the EM-adoption seed test from (3).
6) Docs: update the header comment at modules/Outfits.lua:18-20 and the doc comment at :688-692; docs/schema.md (outfit.icon row, :73, :100); docs/smoke-tests.md WC3 (:230) and a new row "a seeded spec outfit shows its spec icon; Change icon to anything else replaces it; Outfitter chooses brings it back"; docs/test-cases.md (:1275, :1299); docs/testing.md:176.

## Cross-repo
none. NS.Triggers, Compat.GetSpecializationInfo and the fileID path are all in this repo. 132724 is a plain Blizzard fileID, so the LibKa0s icons line in CLAUDE.md is unaffected. ph:coat-hanger must stay declared there as long as the sheet button and broker use it.

## Risks
- Changing NS.Constants.DEFAULT_OUTFIT_ICON in place would also change the gold sheet/dock button (Dock.lua:309) and the broker idle icon (Broker.lua:54), tinted with of.sheet.button. A tinted 132724 would look wrong. Split the constant.
- The spec rung must stay below ownIcon and must not apply to EM mirrors, or it could hide an EM set's own icon. EM mirrors have no builtin today (COPY at EquipmentManager.lua:46), so a builtin-keyed rung in chosenIcon is safe. Keep it that way: do not add builtin to COPY without revisiting this.
- The spec index, not the specID, is the key. Spec order per class is stable, and the data is per character (db.char). If Blizzard ever reorders a class's specs, SPEC_n would point at a different spec; the trigger has the same exposure today.
- Before the spec data is ready (early login), NS.Triggers.Get("SPEC_n") returns nil. The rung then falls through to the trigger, item and 132724 rungs, and the next redraw corrects it. Seeding itself waits 1 s after PLAYER_ENTERING_WORLD.
- Combat and taint: draw-time reads only. The icon path has no protected calls; GetSpecializationInfo is AllowedWhenUntainted and its result is PlainNumber-guarded. No new event registration.
- Standards: the change goes through NS.OutfitIcon, the single resolver, and O.SetIcon/schema rows. No new SavedVariables, no migration, so no schemaVersion step and no deviation-register row. The new constant belongs in core/Constants.lua.
- Behaviour change: every multi-item outfit with no own icon (for example Normal, image 2) switches from the white hanger glyph to the edged chest-art 132724. Every outfit without an own icon, trigger icon or single item looks alike, and the visible distinction from glyph icons goes away.

If they show the hanger, the cause is likely outfits seeded with icon nil, a cleared or changed trigger, or a legacy import. Which character or outfit should be checked?
- After a player picks "Outfitter chooses" (the 134400 wildcard) on a seeded spec outfit, should it go back to the spec icon (the recommended reading) or show 132724?
- Is 132724 the last rung only, keeping the trigger-icon, Birthday Suit and single-item rungs ahead of it, or should it replace all of them for non-spec outfits? Recommendation: keep the rungs and replace only the coat-hanger fallback.
- Should the sheet button and broker idle icon stay the gold coat hanger while outfit rows move to 132724? Recommended: yes.
- If an Equipment Manager set is already named "<Class>: <Spec>" at seed time, should the seed still adopt it (set its builtin and trigger) without touching its icon, or leave EM mirrors out of the spec seed altogether?
